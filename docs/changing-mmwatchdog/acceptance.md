# MMWatchdog acceptance contracts

MMWatchdog's acceptance contracts define correctness for the current
build. The acceptance contracts state the required workflows and outcomes,
what is out of scope, and when work is complete. Use the acceptance contracts
for completion and review.
The [release plan](design/README.md) owns the agreed design, the status of
each feature, and the remaining work. The [validation record](validation.md)
holds the latest results.
The [Standalone acceptance checks](#standalone-acceptance-checks) and
[Fleet checks](#fleet-checks) tables map each contract to the tests that check
the contract. The [testing guide](testing.md) says how to run the contract
tests.

## Acceptance contracts

Each contract names a workflow MMWatchdog must get right and its required
outcome. When a feature is implemented, add a row to the standalone or fleet
acceptance contracts table. Include the feature's tests in the corresponding
checks table.

### Standalone acceptance contracts

The acceptance scope is one Linux/systemd node running the standalone CLI and
daemon, with configured check groups, alert destinations, the heartbeat socket, and an optional
HTTPS heartbeat receiver in MMWatchdog. The standalone acceptance contracts below define
MMWatchdog's correctness on a standalone node:

| Workflow | Required outcome |
| --- | --- |
| Look at the readings | `mmwatchdog readings` and `mmwatchdog fleet readings` read history files directly and read-only, even when MMWatchdog on the command's machine is stopped. Each reading retains the limits in effect during the reading's run. Text output marks readings above upper limits and below lower limits, and includes summaries. JSON output includes every reading. Node-group views show nodes with breached limits first. Node-group views compress only nodes with readings and no breaches. `--chart` draws each measurement against the recorded limit, preserves spikes and gaps, and lists every breach by time |
| Configure and deploy | The complete configuration directory selected by `--config-dir` separates node settings, `check_groups/*.yml`, and alert destinations. Node settings never contain check groups. All check-group files must use `.yml`. Duplicate check group names identify the locations of each definition, and at least one check group is required. Every ordinary check group states `check_every`, `time_limit_per_run`, `alert_after_failing_for`, and `recovered_after_healthy_for`. A direct event check omits `alert_after_failing_for`. None of the four timings has a node-wide default. A duration can count whole days, such as `7d`. A named check may state `alert_after_failing_for` and `recovered_after_healthy_for` independently of the check group's values. For `alert_after_failing_for` and `recovered_after_healthy_for`, `mmwatchdog config` shows whether the check or the check group supplies the value. Invalid candidate configurations, including invalid alert settings, leave the running configuration intact. Accepted settings control the behavior described for each setting. The inventory variable `mmwatchdog_config_source_dir` selects each node's complete configuration set. Switching configuration sets removes obsolete check groups while preserving secrets. An unchanged deployment preserves the daemon, and all three staging copies report unchanged. Alert destinations live under `destinations:`, and each destination names one module and states `alert_severities`. Each destination that takes reminders states `remind_every` as a positive duration or `never`. Every node states `alert_severity_when_this_node_goes_silent`, `alert_severity_when_this_node_has_rebooted`, `keep_measurement_history_for`, and `measurement_history_size_limit`, without defaults. Every hub states `keep_measurement_history_of_nodes_for` and `measurement_history_of_nodes_size_limit` in `fleet_hub_role`, without defaults. `mmwatchdog validate` and `mmwatchdog reload` print validation warnings for a valid configuration. A validation warning never makes a configuration invalid. `mmwatchdog validate --json` carries each kind of validation warning as a list of its own. Secret files readable by the file's group or by every account are refused unless the configuration block naming the secret explicitly permits access. Only read bits count. The shipped workflows open a whole-node maintenance window, with reason `mmwatchdog deploy`, only when a deploy restarts a running MMWatchdog. The maintenance window opens just before the restart and closes once MMWatchdog answers again. A failed deploy leaves the maintenance window to expire. A first install and an unchanged deploy open no maintenance window. |
| Validate configuration on the node and elsewhere | Required settings follow [Configuration files reference](../reference/configuration-files.md#node-settings), including the explicit choice to record readings. Public JSON never includes a destination's credential fingerprint. Listening addresses must include an explicit local host. Validation rejects an address without a host and prints examples of valid listening addresses. Plain `mmwatchdog validate` checks node files and accounts; `--config-only` checks configuration alone. Reload checks node files and accounts before activation. A refused reload keeps the running configuration. A script's optional `validate_inputs(inputs)` runs after input types are checked. Errors point at the authored input. |
| Deploy modules | A release holds the official extra modules in `official_extra_modules/` beside the `mmwatchdog` program. The file `shipped_with_mmwatchdog_version` records the release version. A deployment project keeps modules of the project's own in `mmwatchdog_external_modules/`. Each source directory holds one directory per module, named after the module. Each module directory holds `module_description.yml` and `module.star` or, for a module of the project's own, `module_executable`. Every deploy with the shipped workflows installs all official extra modules of the release in `/usr/local/lib/mmwatchdog/official_extra_modules` on every node. The workflows also install all modules of the project in `/usr/local/lib/mmwatchdog/external_modules` on every node. A check or alert destination uses an official extra module by naming the module. An MMWatchdog update updates the official extra modules. Deployment runs no MMWatchdog command on the machine that runs MMX. On each node, the workflows copy `official_extra_modules/` and `mmwatchdog_external_modules/` to candidate directories beside the installed module directories. The workflows then make each `module_executable` runnable. Next, the workflows validate the new configuration against the candidate module directories with `mmwatchdog validate --official-extra-module-dir DIR --external-module-dir DIR`. A module and the check or destination naming the module therefore arrive in one deploy. Deployment fails before any live change if the configuration names a module absent from the release and the project, even if previously installed. A module without its description or code stops the deploy before any live change. A project module named after a core module, an official extra module, or a setting stops deployment before any live change. Official extra modules shipped with a different MMWatchdog version than the candidate `mmwatchdog` program also stop deployment before any live change. For each module refusal, `mmwatchdog validate` names the module or the conflicting versions. Node settings naming module directories different from the workflows' installation directories also stop deployment before any live change. As the last change before configuration activation, a copy of each candidate module directory replaces the corresponding installed directory. The installed directories then contain exactly the modules of the deploy. Replacement removes dropped project modules and files added by hand under `/usr/local/lib/mmwatchdog/official_extra_modules` or `/usr/local/lib/mmwatchdog/external_modules`. A changed module file restarts MMWatchdog, because MMWatchdog reads the descriptions of configured modules at startup. The source directories `official_extra_modules/` and `mmwatchdog_external_modules/` are required, even without modules of the project's own. A missing source fails before MMX connects to any node and leaves installed module directories and the running daemon unchanged. |
| Verify a destination without a message | A core destination may implement `VerifiesDestination`, and a script may define `verify_destination(inputs, file_contents)`. Verification reads credentials as for delivery, runs under the delivery time limit, and reports acceptance with one line. A module without verification is reported as unsupported, without executing it. Reload verifies new or changed destinations and prints a manual test command, never a test message; verification failure exits 1 with the new configuration active. Startup does not verify. Daily verification retries failures. An alert queued for ten minutes or a verification failing for ten minutes sends one warn notice to other destinations, and recovery sends one warn notice only after no undelivered alert has waited ten minutes and any failed verification has later succeeded. A failing destination makes status exit 3, or exit 1 when a check has an open failure incident (failure takes precedence over health unknown); the failing destination shows in the output in both cases. An unchanged destination keeps its verification failure, warning notice state, and next verification time across a restart. Deliveries postpone neither an old backlog warning nor the daily verification. The seven official destination scripts implement verification without sending a test message; their pages define each request and exact credential refusal. A connection or certificate failure and HTTP 5xx fail, and an unconfirmed response passes. No verification sends a billable event or consumes a message quota; Slack-compatible hosts other than `hooks.slack.com` receive only a connection and certificate check |
| Run a module that is not core | A check or an alert destination names an official extra module or a module of the project's own by the module's name, like a core module, and writes the module's inputs and the run settings `run_as_user_account`, `run_from_directory`, and `env` below that name; the configuration never states the kind of a module. A name that no core module and neither module directory has is a validation error that says where MMWatchdog looked. Every module that is not core has a `module_description.yml` with its `summary`, `used_as`, inputs, measurements, and examples, and MMWatchdog refuses a description that is not valid, also one whose example is not valid for the module's own inputs. `mmwatchdog validate` checks every check and every destination against the description of its module and refuses an input that the module does not have, a required input that is missing, a value of the wrong type, a module that is used as a check where its description says alert destination or the other way round, and a limit on a measurement that the module does not report, each with the file and the line. A module is a Starlark script, `module.star`, that defines `run_check(inputs, file_contents)` or `deliver_alert(alert, inputs, file_contents)` and touches the node only through the primitives `read_file`, `run_command`, `http_request`, `tcp_exchange`, `udp_exchange`, `read_state`, and `write_state`; MMWatchdog runs it in a child process, `mmwatchdog run-starlark-module`, as the account of the check or the destination, under the time limit and a limit of 10 million steps. MMWatchdog tells the module how long the run has left. A primitive that waits for an answer or a program returns an `error` shortly before the run's time limit. The script decides what the error means. A server that accepts the connection and hangs fails a check whose module treats the error as a failure. The error names the time limit. A module of the project's own can instead be an executable, `module_executable`, that reads one JSON request and writes one JSON result. A measurement in a result is a plain number, and its unit comes from the description. A measurement absent from the module description, a script error, an exceeded run limit, or an invalid result makes the observation unknown. MMWatchdog keeps the module's output for diagnosis. Each check whose module is not core has a state directory of its own, which only the module's account reads and which lasts from run to run; `mmwatchdog check-now` works on a copy, and MMWatchdog removes the directory with the check. A module whose description states `one_incident_for_each_finding` reports findings, and each finding is its own incident. `mmwatchdog describe-module` prints descriptions of modules of every kind. `mmwatchdog module-usage` lists configured modules, each module's kind, and the file and line of each call. A remark appears beside each executable. `mmwatchdog status` shows the kind beside each check whose module is not core. `mmwatchdog` refuses to start, validate, or reload with official extra modules that were shipped with another version of MMWatchdog, and names both versions; MMWatchdog reads every `_file` input of a check as root, requires an absolute path, and passes the contents to `run_check(inputs, file_contents)` or executable JSON, so the module can run unprivileged with root-only credential files; unreadable files make the observation unknown and file contents stay out of stored output |
| Observe and diagnose | Checks share the node's `max_concurrent_checks` limit, and each run has the check group's `time_limit_per_run`. A run waiting in the kernel may continue after the time limit. MMWatchdog releases the run's concurrency slot 5 seconds after the time limit, even while the kernel wait continues. The check is unknown and says that the run has not ended. MMWatchdog starts no new run of the check before the old run ends; `ok`, `confirming_failure`, and `unknown` remain distinct; `mmwatchdog check-now` exposes observations without recording incidents, alerting, or running recovery; with `--count-as-scheduled-run` the daemon starts the check group's scheduled runs at once, the runs count as every scheduled run does, with the check's confirmation, and the next run follows `check_every` later; `--without-daemon` reads the complete configuration directory; direct checks are named after their module; status exits 1 for an open failure incident before 3 for unknown, command errors exit 4, invalid configuration found by `validate` exits 1, and MMWatchdog never uses exit 2 |
| Alert on reboots | Starting in a new boot records one `rebooted` event without a `check_group`, naming the boot time and when MMWatchdog last ran, and alerts at the node's required `alert_severity_when_this_node_has_rebooted` through the ordinary outbox, through the hub on a joined node, where it groups with notices of the same severity; the first start on a node and daemon restarts within a boot send nothing; a whole-node maintenance window open before the reboot or at startup keeps the `rebooted` event local and sends no reboot alert notification |
| Catch a crash loop | A `systemd_unit_crash_loop` check, authored under `checks` and naming its unit with `systemd_unit`, fails when systemd restarted the unit on its own more than `automatic_restarts_above` times within `automatic_restarts_within`, all three required, with the count and last seen exit as evidence, and recovers once the window holds no more than `automatic_restarts_above`; MMWatchdog restarts keep the saved history, so an open incident never recovers because MMWatchdog restarted; manual and MMWatchdog-initiated unit restarts are never counted; a recovery command names its triggers explicitly in `triggered_by_checks`; MMWatchdog generates no crash-loop check or recovery action, and a systemd unit check that names no unit is refused |
| Catch every failed systemd unit | An `every_systemd_unit` check requires `fail_when: a_systemd_unit_has_failed` and watches every unit of the node, of every kind, without a list of them, and is healthy while systemd lists no failed unit; `systemd_units_to_ignore` is required and `[]` leaves no unit out; each failed unit is its own incident with its own failing time, alert, raise, reminders, and recovery, so a second unit that fails while the first incident is open is announced, and a repaired unit sends its recovery while another stays open; every alert about a unit names it in its title, its message, and its `systemd_unit` field; `mmwatchdog status` shows one line for each failed unit and exits 1 while a unit has an open incident; when MMWatchdog cannot ask systemd, the check is unknown, sends at most one cannot-check alert, and keeps the incidents of its units open; a changed or removed check closes the incident of each unit without a recovery; in a fleet the alerts of each unit are grouped by themselves, and each unit has a separate key that MMHotline uses to track the unit's incident; `mmwatchdog validate` names, as a warning, every unit that has its own `systemd_unit_state` check and is missing from `systemd_units_to_ignore` |
| Check authenticated endpoints | A `Host` header selects the virtual host and the TLS name verified; credentials come only from a token or basic-auth file read for each request, never from the URL, headers, or configuration; `trusted_certificate_authority_file` replaces the system trust store; verification is the default and only `dangerously_skip_server_certificate_check: true` disables it on `http`; `expected_http_status_codes` lists the status codes that count as healthy; an unreadable credential file or certificate authority file is unknown, and any answer from the endpoint is failed or ok; runtime validation rejects unreadable credential and certificate authority files |
| Check a TLS certificate | A `tls` check opens a TLS connection to its `address`, host:port with no default port, completes the handshake, and sends nothing after it, so it checks any service that speaks TLS from its first byte and not only HTTPS; it verifies the certificate for `server_name`, or for the host of the address, against the system trust store or, with `trusted_certificate_authority_file`, only against that file, and verification is never skipped; it fails when the certificate expires within the required `fail_when_certificate_expires_within`, such as `30d`, with the time of expiry in its message, and when the handshake fails, the certificate is not valid, or no connection opens within the time limit; it records `certificate_expires_in_seconds` and takes no limit on it; a `trusted_certificate_authority_file` that MMWatchdog cannot read or that holds no PEM certificate is unknown, and runtime validation refuses it |
| Run a shell check | A `shell` check runs its script, unchanged, with `/bin/bash --noprofile --norc -o pipefail -c`, as `run_as_user_account` (the unprivileged account `mmwatchdog` without the input), in `run_from_directory` (`/` without the input), with only the environment that MMWatchdog gives and the variables of `env`; the script is healthy when the exit code is in `success_exit_codes`, which defaults to `[0]`. An explicit list replaces the default. Any other exit code fails the check, and the observation keeps the exit code. An exit code 127 or 126 that `success_exit_codes` does not list is unknown when the last line of standard error is Bash's own message that a command cannot be found (127) or cannot be run (126); the observation then includes Bash's message. A 127 or 126 that a program or a script returned by itself fails the check. A 127 or 126 that `success_exit_codes` lists is healthy. A script that cannot start, runs past `time_limit_per_run`, is ended by a signal, or writes more than 64 KiB to standard output is unknown, whatever `success_exit_codes` lists |
| Watch node resources | Node measurements cover CPU, memory, swap, load, I/O wait, memory pressure, and open files. Load covers 1, 5, and 15 minutes, with a per-core value for each period. Filesystem measurements cover space, inodes, and free space. Disk-device measurements cover busy time and data read and written. Network-interface measurements cover link speed and data received and sent. Systemd-unit measurements cover CPU, memory, and process count. Measurement names include the unit, such as `memory_used_percent`. `fail_when_measurement_above` and `fail_when_measurement_below` state limits beside the check's module. MMWatchdog applies measurement limits for core modules and modules that are not core. A reading strictly above an upper limit or below a lower limit fails, and a reading equal to the limit passes. An unknown measurement name or a limit on a module without measurements is rejected. An unreadable measurement is unknown, never zero. Unknown measurements include memory pressure on a kernel without memory-pressure data and link speed on an interface reporting no speed. A `node_filesystem` check with `alert_severity` fails at that severity when nothing is mounted at the path or the filesystem is read-only. Missing and read-only mounts fail with or without a numeric limit. A `node_network_interface` check with `alert_severity` fails when the interface has no link. A check that only records readings notes a read-only mount or missing link but never fails, alerts, or opens an incident. An unresponsive remote filesystem makes the filesystem check unknown within the time limit. MMWatchdog keeps at most one filesystem query pending for each filesystem. Concurrent checks of the filesystem share the pending query's result, so each check gets a measurement. A failed node CPU, memory, swap, or load check names the five commands using the most of the resource in the alert body. |
| Watch every mounted filesystem | An `every_disk_and_network_filesystem` check applies its limits on space, inodes, and free space to every filesystem that is mounted from a disk device or from another machine, without a list of them, and leaves out what the kernel provides in memory and images that are read-only by their nature; `filesystems_to_ignore` is required and `[]` leaves none out; a filesystem becomes a failed finding when a reading exceeds an upper limit or falls below a lower limit. A read-only filesystem, an unresponsive filesystem, or a filesystem that returns an error instead of size data also becomes a failed finding. Each finding is its own incident, with its own alert and recovery, named by the filesystem's mount path; a filesystem that is mounted at several paths is covered once and is ignored by any of its paths; a filesystem that does not answer takes no time from the others; a limit on inodes does not apply to a filesystem without a fixed inode count; `mmwatchdog validate` names, as a warning, every filesystem that has its own `node_filesystem` check with a limit and is missing from `filesystems_to_ignore` |
| Watch one program of a unit | A `systemd_unit_commands` check names its `systemd_unit` and a text, `fail_when_no_command_contains`, both required, and is healthy while one of the commands that `systemctl status` lists for that unit, and for no other program of the node, contains the text; when none does, the check fails and the body of its alert lists the commands that the unit runs; a stopped unit runs no command and fails the check, and so does a unit that systemd keeps active after its last program has ended; a unit that systemd does not know is unknown |
| Check a Unix socket and another machine | A `unix_socket` check is healthy when a connection to the socket at its absolute path opens, and fails for a missing socket file, for a socket that no program accepts connections on, and at the time limit. A `ping` check asks a machine, by its name or its address, to answer the kind of request that the `ping` program sends, which MMWatchdog sends itself: up to three requests in each run, healthy at the first answer and failed when none arrives within `time_limit_per_run` or when the name has no address; it reports `round_trip_milliseconds`, which can take a limit, and a run by an account other than root is unknown and says so |
| Check common services by their protocol | A `tcp` mapping can send `text_to_send`. With `reply_contains` or `reply_matches_regex`, the reply must contain at least one byte and satisfy every configured reply condition. Without a reply condition, `tcp` only connects, like a check written as an address alone. A `udp` check sends text in one packet. The check is healthy when a reply satisfies every configured `reply_contains` and `reply_matches_regex` condition. The check fails at the time limit or when the machine reports that no program listens. `ssh` reads an SSH server's greeting without logging in. `smtp`, `imap`, and `pop3` wait for a greeting, exchange the required protocol responses, then leave. Each mail check requires `connection_security`: `starttls`, `implicit_tls`, or `unencrypted`. Certificate verification is enabled by default. `dangerously_skip_server_certificate_check` explicitly disables certificate verification, and `trusted_certificate_authority_file` optionally supplies trusted authorities. A failed check names the failed protocol step. `dns` constructs a DNS query and sends the query only to the configured DNS server. The node's resolver and hosts file take no part. The query requests all records of one type for one name. MMWatchdog uses UDP first, then repeats the query over TCP if the response is truncated. With `expected_record_values`, the returned values must exactly match the configured set, in any order. TXT values compare exactly. Host names ignore case and a final dot. `udp` and `dns` try every address of a server named by a host name. `memcached` requests server statistics and reports `current_connections`, `cached_items`, and `cache_used_percent` from the returned values. When `bytes` is absent, `cache_used_percent` is omitted. The check also reports `cache_hits_per_second`, `cache_misses_per_second`, `cache_hit_percent`, and `cache_evictions_per_second` from counter changes since the previous run. Counter changes distinguish a cold cache from a warm cache regardless of totals since server startup. Every measurement takes a limit, and a period without gets has no hit ratio. `redis` requires `connection_security: verified_tls` or `unencrypted` on every check. TLS supports a trusted certificate authority file and the explicit certificate-check override. The check sends `PING` and expects `PONG`, after a login with the password of a `login_password_file`, when the check has one. MMWatchdog reads the password for each run and never shows the password, even when the server echoes the password. Every address is host:port with no default port. A connection failure or an answer that misses the time limit fails the check, with wording distinguishing connection failure from reply timeout. The alert body includes unexpected server replies and partial replies received before the time limit. MMWatchdog reads no more than a fixed limit of each server's answer, regardless of how much the server sends. |
| Check database servers, containers, and SQLite databases | `postgresql` uses `psql`, and `mysql` uses `mariadb` or `mysql`. Without database login credentials, the clients connect through the node's local database socket as operating-system account `postgres` or root, respectively. No database account or password needs setup for the local-socket connection without credentials. With database login credentials, `postgresql` uses `login_role`, and `mysql` uses `login_user`, with the password from `login_password_file`. Clients with database login credentials run as the unprivileged account. A check can connect to the local server or, with `database_server_host`, to a remote server. The password reaches the client through the environment, never an argument, and `psql` never prompts for a password. A network check using `database_server_host` requires `connection_security`, and a local-socket check states no connection-security setting. `verified_tls` encrypts and verifies the certificate for `database_server_host` using the node's certificate authorities or `database_server_certificate_authority_file`. `dangerously_skip_server_certificate_check: true` skips server authentication while retaining encryption, and `unencrypted` never encrypts. MMWatchdog sets the client's connection-security options in the client's syntax. A server violating the check's `connection_security` fails the check. An invalid certificate fails `verified_tls` unless certificate checking is explicitly disabled. A server without encryption fails `verified_tls`, even with certificate checking disabled. MariaDB must detect the required encryption and certificate failures before sending login credentials. A server accepting only encrypted connections fails `unencrypted`. A certificate authority file unreadable by the client's operating-system account makes the check unknown and fails on-node validation, using MMWatchdog's wording. `postgresql` and `mysql` report `connections_used_percent` and `replication_lag_seconds`, which take limits. A server that is not a replica has zero replication lag, so the same lag-limited check fits a primary and replicas. A server without an available lag value, such as a group-replication member, has no lag reading. `mysql` also reports `innodb_history_list_length`, which takes a limit. MariaDB supplies history list length through a status variable available to every account. MySQL supplies history list length through an InnoDB counter requiring `PROCESS`. A refused statement makes only the statement's measurement unavailable. A MySQL or MariaDB replica fails when receiving or applying changes from any source stops, including a named MariaDB source. The failure names the source, and replication lag is the greatest lag among the replica's sources. A PostgreSQL replica connected to the primary has zero lag when all received changes have been applied. A replica configured for streaming fails without a limit when the primary connection is lost. A standby replaying only copied WAL does not fail for lacking a streaming receiver. `postgresql` reports `transaction_ids_used_before_wraparound_percent` with or without a login, on a primary and a replica: `100 * max(age(datfrozenxid)) / 2147483648` over every database, including templates. The reading takes a limit, with no default limit. An age that cannot be parsed has no reading. `postgresql` reports `cache_hit_percent`: the share of blocks read since the previous run served by shared buffers. A period without reads has no cache-hit reading. `wal_archive_lag_seconds` measures how long the oldest finished write-ahead-log segment has waited for archiving. The archive lag is zero when no segment waits, including on a server without writes. A replica also reports zero unless `archive_mode` is `always`, because the primary archives. A former primary now running as a replica also reports zero, even while segments from its time as the primary still wait. A primary with `archive_mode` off has no archive-lag reading. A check with database login credentials has no archive-lag reading, because PostgreSQL lists waiting segments only to administrators and `pg_monitor`. A server that does not answer or refuses the login fails the check with the client's first output line. A node without the client program makes the check unknown. `pgbackrest` runs `pgbackrest info --output=json` for the configured `stanza` as operating-system account `postgres`. `latest_backup_age_hours` measures hours since the latest error-free backup of any type finished. The check fails for a stanza or repository problem reported by pgBackRest, with the first line of each repository's reason. The check also fails when every backup found damaged pages, or when `pgbackrest` fails or exceeds the run's time limit. The message names a newer backup with damaged pages and any running backup. A node without `pgbackrest` makes the check unknown. `docker_container` uses `docker` to ask whether the named container runs. The check fails for a stopped, paused, repeatedly restarting, or removed container, or a container failing the container's own health check. If MMWatchdog cannot ask Docker, the check is unknown. `sqlite_database` opens another program's database read-only and changes nothing. The small query and, with `check_integrity: true`, SQLite's check of every page run as ordinary readers under SQLite's locks. The readers see one finished database state, including while SQLite copies log changes into the database file. A program that waits for locks as SQLite requires gets no error from concurrent monitoring reads. The check fails only when SQLite finds damage, and every other SQLite error is unknown. The query and integrity check run only on a database with a write-ahead log. Review related paths together: reload with running observations, maintenance
with failing times and recovery actions, and storage failure with every state-changing entry
point. The [acceptance checks](#standalone-acceptance-checks) map
the standalone acceptance contracts to focused tests and the short Linux
workflow suite.

The contracts describe outcomes for the typical deployment: one operator,
working directly or through a coding agent, with a single node or a fleet of
a few dozen, rarely more than 100. The operator and the people they grant
access are trusted; guarding against their misuse is out of scope. MMWatchdog must also stay fast and usable up to the
10,000-node lab, which the [load run](testing.md#large-fleet-load-run)
checks: scale work that keeps it so belongs in the code, but findings are
judged against the typical deployment. Absolute words in the contracts state
the outcome in ordinary operation, not a promise about every conceivable
interleaving.

The acceptance and review rules serve MMWatchdog's goals: correct behavior,
security, reasonable speed, and ease of use. Judge a finding by whether the
finding threatens correct behavior, security, speed, or ease of use in
practice, not by whether some sentence can be quoted against the code. Work
that improves none of MMWatchdog's goals is unrelated to acceptance and review.
Leave work unrelated to MMWatchdog's goals out.

A correctness blocker must violate a standalone or fleet acceptance contract in
a supported workflow. Evidence must include a reproduction or a directly
demonstrable code path. The typical deployment must plausibly encounter the
violation in ordinary operation. The violation must cause at least one of the
following outcomes:
loss of data, a leaked secret, a wrong or missing alert, an unnecessary
service restart, a real problem hidden from the operator, an incorrect
status or exit code, an action by an untrusted party, or a stopped workflow.

A scenario that needs several unusual checks at once or precise timing, or
that costs only a delay, a duplicate the design accepts, or a slightly wrong
message, is not a
blocker. Fix a blocker and verify related paths before
closing the finding.

Every fix adds code the next reader must follow, and MMWatchdog stays small only if
most findings are dropped. Record an improvement only when the typical
deployment plausibly meets it in ordinary use, its loss is real, and its fix is
small. Drop everything else. Design text the code does not implement, a
mistake in the operator's own configuration that MMWatchdog already makes visible, and
a cosmetic difference are not findings: correct the text, or leave the text as
it is. Prefer
fixes that remove code, and add no mechanism for a case that neither the
typical deployment nor the 10,000-node lab will meet.

A feature is complete when its contract checks pass, the implementation
and guides agree, and no known correctness blocker remains. Report the commands,
results, and specific unverified boundaries. Once the feature's contract checks
pass, the implementation and guides agree, and no known correctness blocker
remains, stop the acceptance pass.
Reopen the acceptance pass for a concrete failing contract, a changed
requirement,
or a code change affecting that contract.

Ordinary outages, failed checks, daemon restarts, rejected reloads, unavailable
receivers, and disk-full/write failures are in scope. Exhaustive combinations of
faults, adversarial sequences of trusted operator commands, sub-100ms scheduling,
maximum-size configuration stress, hardware/power-loss testing, and multi-day
soaks are not routine completion gates. The excluded tests and fault
combinations require a concrete deployment need or observed failure. The limits
on routine acceptance testing do not relax
input validation, credential handling, data-loss protection, or bounded recovery. Existing focused failure
tests remain useful. New tests should prove a contract rather than enumerate
every imaginable sequence.

The following node-check requirements define how the acceptance contracts
handle incomplete evidence. Node checks must not report incomplete evidence
as confirmed health.
Unreadable sensors, array data, process lists, and log lines follow the
unknown-result rules of each check's module.

Filesystem permission errors remain findings, including errors for long mount paths.

Security-update checks require package lists and a recent success stamp.
Without the stamp the check is unknown, even with fresh lists.

Log matches
keep the run failed even when a later read fails. Oversized lines advance after MMWatchdog checks the oversized lines' prefixes.
Rotated backlogs do not hide a fresh current log.

Recovery messages retain a long filesystem path after a daemon restart.

Review related paths together: joining and replacement with reports in flight,
hub restarts and maintenance windows with the deadlines for declaring nodes
silent, alert fallback with fleet alert grouping and late delivery, and storage
failure with every hub write. The hub and
joined nodes follow the [fleet implementation rules](implementation-rules.md#fleet-reporting).

The standalone definitions of a correctness blocker, of an improvement worth
recording, and of completion apply unchanged. Ordinary node loss, hub restarts and outages, unreachable
networks, rebuilt nodes, and a full hub disk are in scope. Rare duplicates and
late alerts around a hub outage are accepted, as is the case where the hub and
all of its hub-outage alerters fail together. Several hubs, adversarial network timing, clock
attacks, and multi-day large-fleet soaks are not routine gates. The accepted
rare cases and the exclusions above do not relax authentication, input limits,
or data-loss protection.

For a full standalone acceptance pass, run Go tests with the race detector,
`go vet`, the Python environment tests, the native Linux Go tests, and the
affected VM workflow suites on Debian 13 and Ubuntu 26.04 after an ordinary
change. At the end of a stage, run the stage's new and changed suites once
on every target distribution, as the [testing guide](testing.md#test-in-levels)
requires. Run short workload coverage against the installed build.
Re-run release deployment when packaging or deployment changes.
Runs on other architectures and extended soaks are additional validation for
changes that affect those architectures or what a soak measures, rather than
repeated gates for every fix.

For a focused change, run the affected contract tests and relevant Linux
workflows. Check the final diff against the acceptance contracts,
record any concrete remaining blocker, and finish once the applicable checks
pass. Do not expand a passing acceptance run into another speculative review
or add an exhaustive fault matrix. New failures or requirements justify
additional work.
